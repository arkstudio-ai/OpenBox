# Turbo 口播：先备齐素材，再批量生成

在口播任务的有效模型为 `MiniMax-H3-Max-Turbo` 时读取。有效模型取
`person_selected_model`，仅在未选择时使用已向用户说明的 `default_model`。
能力与参数以 `video_generate(action="models")` 和免费 `estimate` 为准；复用本轮
已经读取的能力，不为进入下一阶段重复查询。
普通 MiniMax H3、其他模型及非口播任务不因本说明而切换模型或增加素材卡。

流程：确定素材方式 → 讲稿确认（原卡 1）→ 拆段 → 准备全部所需图片并确认
→ 各段完整提示词、素材与费用确认（原卡 2）→ 并发生成 → 台词及接点核验
（原卡 3）→ 合成交付。图片确认不代替视频费用确认。

## 素材方式：先读已有决定，再询问

沿用用户本次明确指令或同一制作任务的保存记录。用户已说要首尾帧、使用指定
图片或直接文生视频时，不再问一次；已有付费视频任务先按记录继续，不为补走
新流程而重新制作素材。素材存在本身不代表用户已确认用途或同意改图。

没有决定时，用 `question` 问：

这张素材方式卡设置 `allow_attachments=true`，让用户选择“使用已有图片”时
能在同一张卡从资源中心选择或手动上传。后续索取缺少的照片、音频或其他素材时
也启用此字段；回答附带的真实资产可直接复用，不要求用户另发消息或粘贴文件路径。
普通讲稿、费用确认不因此增加素材要求；附图本身仍不代表同意修改图片或支付视频费用。

> 这条口播视频要不要先准备人物画面？可以生成首帧、生成首尾帧，
> 也可以使用已有图片或直接生成视频。

| 选项 | 保存的 mode | 执行方式 |
|---|---|---|
| 生成首帧 (Recommended) | `first_frame` | 准备开场构图；同场景可以复用，提示各段重新从该姿态开始，可能跳切 |
| 生成首尾帧 | `first_last` | 拆段后准备起止画面，同场景相邻段共用衔接图 |
| 使用已有图片 | `existing` | 检查现有图片、明确用途，再逐段绑定；不自动改图或补图 |
| 不需要，直接生成视频 | `text` | 不生图；用同一文字画面基底生成各段 |

选中生成选项即为对应范围的生图请求，不再机械地重复询问许可。此时只保存方式，
不要在讲稿、拆段未确定时提前生成整套图片。实际生图前展示所需张数、用途及
已知费用信息；无生图报价时如实说明，不能声称免费或用视频估价冒充生图报价。
已有明确的预算/张数约定时遵守它，超出范围先取得调整后的决定。

不把“不要生图”自动解释成丢弃已有照片；用户仍要求使用照片时走 `existing`。
用户提供多张人物、服装、场景图时，先明确它们是首尾画面、不同片段的输入，
还是制作新画面的源素材，不能按上传顺序猜首尾，也不能悄悄只取前两张。
使用已有图片不授权修改它；不够用时说明缺少哪些画面，让用户选择补图或调整
片段连接方式。保持问题聚焦，不重复索取会话中已有的主题、人物或素材。

## 拆段后规划整套画面

沿用主流程的 `split_script.py`、`plan_shots.py`，从实时模型能力取时长上下限。
每段按完整语义和台词长度计时，尽量在完整句子和自然停顿处连接。30 秒可以是
2×15 秒，也可以是 3×10 秒，不能把任意稿件硬塞进预设段数。

同一连续场景的 N 段在 `first_last` 模式下通常需要 N+1 张图片。示例：讲稿
确实适合拆为两段各 15 秒时，先准备并确认 A、B、C：

| 片段 | 计划秒数 | first_frame | last_frame |
|---|---:|---|---|
| 1 | 15 | A：开场 | B：衔接 |
| 2 | 15 | B：同一衔接资产 | C：结束 |

内部边界必须复用同一个 `asset_id`，不能生成两张相似的 B 分别绑定。
这些都是预先准备的静态关键帧，不等待第一段视频生成后再截尾帧启动第二段。
确认后两段具备独立输入，可以并发提交。明确换场景的镜头按创作要求切换，
不强行共用边界。只有首帧时尾帧可以省略，不为了凑齐首尾而自动补图。

统一人物、服装、背景、机位、光线和比例，逐帧只调整必要姿态。衔接帧适合自然
停顿和克制手势；尾帧呼应收尾语气。共同图片约束起止画面，但不保证实际视频
动作、声线和语气无缝连续，仍需逐个检查接点。

若仅批准先做样片，准备和生成范围就是该样片；不借样片许可生成整片其余素材。

## 生图、审查与确认

1. 先检查用户源素材。人物、场景和物品应符合其要求；清晰度、手部结构、裁切
   与计划动作要匹配。9:16、半身、实景背景是竖屏口播常用建议；纯色背景、
   特写、不露手或不佩戴领夹麦不是接口错误，不能据此强迫用户重做。
2. 有源图时通过 `image_gen.input_images` 传入真实资产 ID；只有本地图片路径时
   先用平台图片查看工具取得可用资产。无源图且用户要求定制时省略 `input_images`。
   图片来源始终使用平台已有资产通道。
3. 选定共同身份依据：用户原始人物图，或从零生成的主画面。其余关键帧编辑时
   持续使用这份共同依据，必要时同时引用主画面保持布局，避免逐张只引用上一张
   衍生图积累变化。先得到共同依据，再准备其他帧；这是图片准备的依赖，不应
   变成视频片段之间的等待。
4. 使用当前生图模型支持的 `size`，按用户目标比例生成；常用 9:16 示例是
   `720x1280`，不是强制像素尺寸，也不是视频分辨率档位。实际检查输出比例。
   各关键帧有各自用途和提示词，`n` 仅表示同一提示词的候选图数量，不能把三个
   随机变体默认当作 A、B、C。
5. 查看生图结果，检查人物相似度、手部、构图、比例及整套图片的一致性。生图
   提示词表达保持身份的目标，不保证五官绝对不变。保存工具返回的资产 ID，
   复用已有图片卡，不因展示重复上传结果。
6. 集中展示图片和片段用途，用 `question` 给出 `使用这些图片 (Recommended)` /
   `修改指定图片` / `重新生成指定图片`。已有用户明确接受的图片和相同用途不再
   出卡；其他情况必须依据实际答复记录确认，不能把推荐选项当作答复。

只重做用户指定或已说明需修复的范围。初次结果有问题时说明问题，不自动无限
重生；新增付费重生先说明张数、范围和可用费用信息，并取得对应请求。
工具失败或结果不明时保留已完成图片，先查看现有结果和调用记录，不因恢复任务
而把全套素材再生成一遍。不可用的工具或缺失资产要说明，不能伪造资产 ID。

以下为图片提示词模板，按主题填写，删除不适用的建议：

**用原图准备主画面**（有源图时使用 `input_images`）：

```text
以输入人物为身份依据，保持五官特征、发型及用户要求保留的细节。
为“<主题>”准备口播开场静态画面：<用户选择的场景、服装和构图>。
人物自然面对镜头，姿态放松；若计划有手势，使需要活动的手部清楚自然。
比例为<目标比例>，光线自然，不添加未要求的文字、字幕或道具。
```

**从零准备主画面**（用户选择定制，无 `input_images`）：

```text
为“<主题>”制作口播开场静态画面。
人物设定：<已知要求或结合主题提出的形象>；场景、服装：<约定方案>。
<目标比例>、<约定景别>，自然面对镜头，适合开始讲解的姿态。
画面清晰、光线自然；不添加未要求的文字或字幕。
```

**准备衔接帧或尾帧**（引用共同身份依据和主画面）：

```text
保留输入主画面的人物身份、服装、场景、机位、光线和画幅比例。
这张图用作<第 N 段结束与第 N+1 段开始的共同画面 / 最后一段结束画面>。
对应内容是“<相关台词含义，仅供设计姿态，不写到画面上>”。
仅调整为<自然停顿手势 / 收尾姿态>，保持身体位置与背景布局一致。
不额外换装、换景、增加人物或文字。
```

## 工具参数与素材记录

当前 RunningHub 接入支持 JPEG/PNG/WEBP 首帧、可选尾帧；视频时长 5–15 秒，
分辨率 480p/768p，提示词不超过 2048 字符。制作开始或模型、分辨率改变时读取
`models`，并对各段完整请求运行 `estimate`，不把这些数字当永久能力表。
视频分辨率遵循用户的实际选择。

- 有图：每段明确绑定 `first_frame`，按需要增加 `last_frame`，使用 `ratio="adaptive"`。
  输出比例继承首帧，不能仅修改 `ratio` 来替代准备正确比例的图片。
- 无图：`input_assets=[]`，传用户要求的显式比例，竖屏默认 `9:16`。
- 不传普通 `reference_image`、视频参考或音频参考；不只传一张 `last_frame`。
  人物、服装、场景源图可以用于已获请求的生图合成，视频输入只传最终确认的帧。
- 每段用显式时长；本渠道不支持 `-1` 智能时长、seed、静音或添加水印。
- 提示词描述画面动作和逐字台词，不写资产 ID、URL；角色和资产绑定在结构化参数中。

沿用当前制作任务的 slug 和 `state.py`。它是记录本，不是自动授权或后台工作流。
用 `set --key turbo_frame_prep --value <JSON>` 保存模式、实际选择依据、准备状态、
目标比例、源图、帧 ID 与用户确认记录；`set --value` 保存的是 **JSON 字符串**，
读取 `show` 时按 JSON 解读这个字段，不能假定脚本自动解析或执行其中状态。
选择已确定但图片未确认时用 `status="planned"`；用户接受具体图片及用途后才写
`status="ready"`。文生模式在明确选择后可以直接 ready，帧列表为空。

下面是用户已经确认 A/B/C 后的记录示例，实际使用工具返回的 ID：

```bash
python3 "$S/state.py" set --slug <slug> --key turbo_frame_prep --value '{"model":"MiniMax-H3-Max-Turbo","mode":"first_last","status":"ready","ratio":"9:16","decision_note":"用户选择生成首尾帧","source_asset_ids":["person-source"],"frames":{"A":"asset-a","B":"asset-b","C":"asset-c"},"confirmation_note":"用户确认 A、B、C 及其片段用途"}'
python3 "$S/state.py" shot --slug <slug> --index 1 --assets '{"input_assets":[{"asset_id":"asset-a","role":"first_frame"},{"asset_id":"asset-b","role":"last_frame"}],"ratio":"adaptive"}'
python3 "$S/state.py" shot --slug <slug> --index 2 --assets '{"input_assets":[{"asset_id":"asset-b","role":"first_frame"},{"asset_id":"asset-c","role":"last_frame"}],"ratio":"adaptive"}'
```

`shot.assets` 也是 JSON 字符串，已有确认哈希会跟踪这个字段。实际 `estimate` /
`submit` 使用其中的 `input_assets` 和 `ratio`，并结合该段已记录的完整 prompt、
时长、模型与分辨率；不能把整段 JSON 或 A/B/C 标签当作 `asset_id`。
文生模式也明确记录 `{"input_assets":[],"ratio":"9:16"}`（按实际比例替换），
避免沿用之前模式的图片。仅写顶层准备记录不会改变逐段确认哈希。

替换 B 时，将准备状态改回 planned，并同时更新第 1、2 段的 `assets`；A 或 C
变化只影响引用它的段。同一首帧被所有段复用时，换图影响所有这些段。
重验并确认受影响图片后，重写相应请求、免费估价并重出原卡 2；旧 take 不能
冒充新素材方案的结果。记录新的不同 job 时，`state.py shot --job` 将旧结果及
接受记录归档到 `previous_takes`，新 take 需要重新记录和验收；新 job 返回前
也不能把尚未替换的旧结果用于新方案。保留历史但仅在取得对应新 take 后合成。
修改整个身份/场景、拆段或模型时重新评估所需帧和用途，复用仍然适用且被接受的
图片。恢复时保留已记录选择，不因新一轮对话而自动重问、重生或丢弃已付费任务。

## 全部准备完成后才提交视频

回到主流程原卡 2 前，当前批准范围内所有片段都应具备：实际存在且已接受的
图片（或明确文生选择）、完整台词及提示词、素材角色、显式时长、当前模型与
分辨率，以及每段准确请求的免费估价。用户在原卡 2 确认后，才批量提交。

在渠道并发限制内一次提交这些独立请求，立即保存各段 job_id，再共同查询。
不边生成视频边补下一段图片，也不把后台排队误判为需要重新下单。
已完成片段可先做质检；全部片段就绪后按 [quality.md](quality.md) 检查真实接点，
将画面、动作、声音、停顿和时长问题并入原卡 3，再合成交付。
