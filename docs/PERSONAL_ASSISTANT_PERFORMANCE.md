## 改动如何保持原有正确性

- **只在一个边界内复用。** 每次挂起检查、每个派发检查点、每个顶层校验各自新建作用域，调用结束即丢弃；绝不跨边界、跨事务、跨提供方检查点复用。事实在第一次需要时读取一次，等价于这次检查对该事实只读一次。
- **边界结束时再读当前授权。** 共享读取的图遍历完成后，以不缓存的方式重新读取成员资格和私有主会话。PostgreSQL 回归覆盖了“遍历中途由独立事务撤权”的情况，检查结论为不可用。
- **新鲜读取仍不缓存。** 派发检查点本身的业务读取和任务快照（`fresh=True`）保持原来的逐项重读与重新取数比较。
- **写入即停止复用。** 边界内发生刷新、非 SELECT 语句或出现未刷新修改，复用立即停止；存在待提交修改、保存点，或另一个 Session 已持有遍历时，直接走原来的逐边读取。
- **持有行先比对指纹。** READ COMMITTED 下后续读取可能原地刷新同一 ORM 行。原始行和结果行带内容指纹，指纹变化即重读并重新校验哈希，且本边界剩余部分不再复用。
- **组证明等价于逐个命令证明。** 组证明是其包含的命令证明的并集及最大高度，在新位置读取时检查的环和路径深度与逐个读取命令证明完全相同；每个派生仍各自计算来源预算。组证明归属产生它的事实作用域，失败或超出容量的组不保留。
- **监视器节奏不影响派发。** 暂停、取消控制在同一事务中写 `abort_requested_at`，监视器每 0.5 秒照常读取；只有依赖完整来源回放才能发现的撤销改为最多约 5 秒发现。所有模型、工具和沙箱派发前的挂起检查不变。

## 上一轮诊断：4,495 次查询从何而来（`9d9a85b4` 之前）

以下为本轮改动前的诊断，保留作对照。放大路径 1～3 的重复读取已由边界内复用和组证明处理；4 中同一观察的重复验证已在边界内按观察摘要只做一次，但每次验证仍使用自己的独立只读快照；5 的约束仍然成立：不同边界之间不复用任何事实。

**这个数量明显过高，反映了来源校验实现的查询放大。权限正确性有必要保留，但不能把当前往返次数都解释为必要成本。**

### 放大路径

1. [`scheduling.py`](../backend/assistant/scheduling.py) 的 `_held_task` 会校验计划来源、任务命令来源及继续执行权限。它不是只查一条 Task 状态。
2. [`command_sources.py`](../backend/assistant/command_sources.py) 的 `validate_command_derivation` 展开命令保存的原始消息、业务读取、决策和任务快照；每个命令建立自己的消息/引用验证集合。
3. [`evidence.py`](../backend/assistant/evidence.py) 在获取原始行后仍继续验证其来源依赖，结果和历史消息又可能引回任务及命令。这次记录有 4,985 次 `validate_source_ref` 调用、327 次消息证据请求、482 次 Result 请求；函数调用数不等于 SQL 次数，但显示了遍历规模。
4. 记忆和知识来源的验证进入各自的新只读快照，再检查权限、当前版本、删除/遗忘状态和正文。该调用内新增了 **98 个**快照事务：知识验证 56 次（含 21 次正文读取验证）、记忆验证 42 次。原始指标的 `read_only_transactions=100` 还包含诊断基线 1 个事务及预先建立的外层 1 个事务，不能写成“函数新建 100 个事务”。这些观察的唯一身份数量未在此诊断中记录，不能把 98 次都称为完全重复。
5. [`transactions.py`](../backend/assistant/transactions.py) 中的 `SnapshotChecks` 只在明确的同一只读快照内复用事实。执行准入、工具调用及模型派发的当前权限检查不能直接复用历史页面的旧验证结果；外层 READ COMMITTED 的相同参数查询也可能读到中途撤权。

原始行缓存已经工作，并非简单的“没开缓存”：命令原始行 777 次请求只有 69 次实际读取，来源原始行 1,300 次请求只有 248 次实际读取，Result 482 次请求只有 34 次实际读取。该次 CommandWalk 仅有 14 份证明、443 份原始读取记录，未达到 512 的容量上限，也没有失效。因此继续扩大容量不能解释或解决这次查询放大；命中原始行后仍进行的来源遍历、当前事实查询和独立快照读取需要结构性改进。

## 候选结构改造：单次校验降到 5～9 条 SELECT

**状态：仍未实施，也未迁移或实测。** 本轮在不改表结构的情况下，用边界内复用把同类单次校验从约 6,350 条降到约 1,120 条 SELECT。本方案的个位数目标以及跨边界复用，仍是进一步降低每个边界成本的方向；5～9 是原型设计预算，不是已有结果或性能承诺。整个任务经历多次模型和工具调用，各执行边界仍需要当前授权检查，不能共用一次旧证明。

### 需要解决的数据结构问题

目前关键来源关系保存在 `AssistantCommand.source_ref` 和 `AgentEvent.payload` 的 JSON 中。Python 沿引用逐项展开，读取原始行后又验证它们的来源；记忆、知识观察各自建立快照。仅优化 SQL 构造、补索引或把局部查询连表，不能消除这套遍历与事务安排产生的全部放大。

建议增加可重建的关系投影，原始事件、命令和证据继续保留。以下名称为设计示意，并非已存在或已确定的数据库表：

| 关系投影 | 应保存的信息 | 用途 |
| --- | --- | --- |
| 证据节点 | 完整来源身份、actor/workspace 范围、版本、正文/观察哈希、原记录引用 | 区分同一对象的不同版本，批量定位唯一依赖 |
| 依赖关系 | 父子节点、关系类型、原始顺序、时间截止点 | 通过索引与递归 CTE 一次获取有界依赖图 |
| 投影完整性 | 根记录及摘要、解析版本、连续事件前缀/水位、完整状态 | 证明没有漏边；未回填或未追平时不能把缺失关系当作“没有依赖” |

依赖边必须从已核验的原始证据和实际模型消费记录建立，不能只因 JSON 中有引用就授予可信资格。节点去重键必须包含完整观察身份与版本，不能只按 `part_id`、文件 ID 或 Task ID 合并。同一来源的冲突版本、不同分页窗口和空结果观察都要保留各自语义。

### 批量查询预算

先收集依赖图，再按来源类型连表读取事实，在内存中按原始顺序执行哈希、范围和图规则校验。查询可以使用递归 CTE、集合条件及分组读取；需要避免多对多关系连表产生大量重复行。PostgreSQL 支持递归查询和环检测，仍需显式控制范围并处理超限，不能静默截断依赖。[递归查询文档](https://www.postgresql.org/docs/current/queries-with.html)

| 一次校验中的工作 | 目标 SELECT 数 |

这是 SELECT 预算；事务控制、写入和整个任务的其他 SQL 另行计数。验收还要检查数据库内部执行次数、扫描行数、返回字节量及耗时，不能通过把循环查询包进一个函数或存储过程来宣称工作量下降。

### 事务与正确性问题

- **需要重新定义阶段边界。** 保持现有 98 个独立读取时点完全不变，无法同时压到个位查询。新方案要明确哪组事实共享快照，以及最终授权以哪个当前读取时点为准；这是事务语义改造，不是机械替换 JOIN。
- **最终检查必须能看见新变化。** 准备阶段的旧快照不能代替模型或工具派发前的权限、来源版本、任务状态检查。REPEATABLE READ 事务内重查仍看不到其他事务在其快照建立后的提交，不能将这种重查误称为新鲜授权。[事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)
- **已有节点之外也有依赖。** 新增来源、目录集合变化、分页和空结果可能改变原观察。需要重新执行有界谓词检查，或使用与相关变更同事务维护的范围/集合版本；未经完整写入路径验证的异步失效通知不能成为正确性依据。
- **保持已有拒绝规则。** actor/workspace 隔离、撤权、遗忘、删除、原始内容哈希、来源缺失、拒绝优先级、逐路径循环/深度/数量预算，以及 run/generation/Inbox/事件前缀等执行约束都要保留。全局去重不能隐藏另一条路径的超限。

下一步原型首先要补齐“完整观察身份及版本”的唯一基数和各派发边界的触达记录。目前的诊断没有该基数，不能先假定 98 次观察全部可以合并。

### 迁移与验证路径

1. 新增投影表和按作用域、根节点、依赖节点组织的索引；原表继续作为原始证据。
2. 在原始记录提交的同一事务中双写投影，明确所有内容、权限、遗忘及集合版本变更的维护路径。
3. 有界回填历史数据，核对原始摘要、实际消费证明及连续完整前缀。缺少原证明的旧记录不能因回填而变为可信；投影未完成时走旧校验或拒绝。
4. 在相同固定数据上对照新旧校验的正文投影、允许/拒绝结果和错误顺序，覆盖独立事务撤权、修改来源、空结果/分页变化及失败回滚；对照只运行校验，不能重复执行模型或工具副作用。
5. 切换已通过对照的路径，测量实际 SELECT 数、数据库工作量和正常运行延迟，再用原无影任务完成浏览器复测。达到查询预算且正确性、整体耗时都通过后，才关闭相应性能子项。
