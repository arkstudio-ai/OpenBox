# RunningHub 快速视频档位

新增 `fast` 视频档位：**快速 / MiniMax-H3-Max-Turbo**。本地配置和配置示例默认选择 768p、5 秒，每 5 秒查询。已有质量、标准、灵活档位保留；既有会话的模型和分辨率选择优先，新对话才使用部署默认值。聊天模型仍然只有原来的三档。

## 路由与输入

使用既有 `video_generate` 工具和持久化 VideoJob，新增 `runninghub` 协议适配器。用户选择一个模型；后端按本次明确使用的 `input_assets` 确定端点，不用提示词关键词猜测，不把历史中的无关图片自动带入。

| 本次输入 | 调用 |
| --- | --- |
| 无素材，纯文字 | `/openapi/v2/minimax/h3-max-turbo/text-to-video` |
| 一张图片，模型按用户意图明确标记 `first_frame` | `/openapi/v2/minimax/h3-max-turbo/image-to-video`，传 `firstFrameUrl` |
| 两张图片，明确标记 `first_frame` / `last_frame` | 同上，同时传首尾帧 URL |
| 视频、音频、超过两张图片、无法确定首尾的两张图片 | 付费前拒绝；请求用户明确素材角色或切换兼容模型 |

图片数量不是意图。对话模型先结合用户描述、图片内容和实际资产 ID 判断用途，再填写结构化角色；后端只校验并执行，不读上传顺序猜首尾。单图未指定角色或标为普通 `reference_image` 也拒绝，防止把产品/人物/风格参考误当起始画面。意图明确时直接执行，无须逐次确认；不明确时先问一个聚焦的问题。

例如“第二张开场、第四张结束”绑定相应两个 asset_id；“每张分别动起来”拆成多个镜头、分别绑定首帧并汇总估价；“产品图和模特图一起参考”属于组合参考，Turbo 不支持，不能偷换成首尾帧；只说“用这些图做视频”时先明确是分别生成、首尾过渡还是共同参考。图片数量超过两张不允许挑前两张或丢弃其余请求素材来绕过校验。免费 estimate 返回实际操作及 asset_id→角色映射，便于核对。

共同字段：`prompt`（1–2048 字符）、`resolution`（480p/768p）、`duration`（5–15 的字符串）。文生传六种显式 `aspectRatio` 之一。图生不传比例；省略工具 `ratio` 自动用 `adaptive`，输出继承首帧比例。若用户明确要求另一比例，工具提示先准备相应比例的首帧，不能静默忽略。

API 没有静音/水印开关；不发送 `generate_audio` / `watermark`。工具层请求关闭音频或添加水印会在付费前拒绝。`seed` 沿用现有工具的降级说明，明确返回不支持。JPEG/JPG/PNG/WEBP 可作图片输入。

认证只由后端发送 `Authorization: Bearer …`。实际业务图片沿用 FileAsset 所有权校验和短期 OSS 签名 URL；密钥不进入前端、提示词或仓库。

参考：[文生定义](https://www.runninghub.cn/runninghub-api-doc-cn/api-510773975)、[图生定义](https://www.runninghub.cn/runninghub-api-doc-cn/api-510773974)、[查询定义](https://www.runninghub.cn/runninghub-api-doc-cn/api-425767306)。Turbo 没有本次核实过的视频参考接口；完整 H3 多模态是另一个模型，本次没有添加或自动切换到该模型。

## 计费

2026-09-24 用[官方价格预估 API](https://www.runninghub.cn/runninghub-api-doc-cn/api-454850620)验证了文生/图生 × 480p/768p × 5/10/15 秒的 12 个组合；两种操作价格相同，完整无密钥响应在 [价格证据](evidence/runninghub-prices-20260924.json)。

| 分辨率 | 上游元/秒 | 现行积分/秒 | 5 秒 | 10 秒 | 15 秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 480p | 0.22 | 0.22 | 1.10 | 2.20 | 3.30 |
| 768p | 0.34 | 0.34 | 1.70 | 3.40 | 5.10 |

沿用 `billing/rates.json` 的 1 CNY = 1 积分成本定价，本次未另加利润系数。菜单单价、免费 estimate 和最终账本共用此表。按提交的整数秒数计费，实际 MP4 的编码尾部不会增加收费。

提交时将完整服务端报价放进 `VideoJob.request_data.billing_quote`。即使任务执行期间费率表更新或模型下架，结算仍使用原报价；损坏或不匹配的报价禁止扣费。只有视频成功复制到 OSS 并可交付时才结算，`generate:{job.id}` 保证多次查询/恢复只记一笔。参数拒绝、605 余额不足、生成失败不产生成功生成扣费。

沿用现有账本模式：`enforce` 实际扣积分，`shadow` 仅记录，`off` 不记录。本地原有 shadow 模式保持不变；没有修改支付渠道、套餐或全局扣费开关。前置余额校验也沿用现有机制（enforce 下余额必须为正），本次没有引入积分冻结/预授权。RunningHub 官方仍独立向渠道账户收取实际生成费用。

## 任务可靠性

提交只执行一次。保存字符串 `taskId` 后使用 `POST /openapi/v2/query`，支持 QUEUED/RUNNING/SUCCESS/FAILED。成功必须返回可用的 MP4 地址，随后复用现有 OSS 转存、恢复和附件回传流程。路由指纹保留端点和账号身份，不能用另一账号接管旧任务。

HTTP 200 的业务拒绝（包括 605）也进入明确失败路径。提交超时/无有效响应被标为结果不确定，向用户返回任务记录并阻止当前 Agent 轮次换 key 再下单；应核查 RunningHub 任务历史后决定是否重新尝试。已拿到 taskId 但首次数据库写入失败，会保留 taskId 继续恢复。当前接入不声明上游取消能力；沿用现有本地取消说明，上游任务可能继续完成并收费。

## 部署配置

生产发布时仅合并 RunningHub 相关字段，不要用本地示例配置整体覆盖线上文件。

生产启用时，后端环境增加 `RUNNINGHUB_API_KEY`，在 `provider` 追加 `runninghub`（key 用 `{env:RUNNINGHUB_API_KEY}`，base_url 为 `https://www.runninghub.cn`），在 `video_generation.models` 追加配置示例里的 Turbo 能力声明，在 `model_tiers.video` 追加 `fast`。将 `video_generation.model/default_resolution/default_duration` 设为 `MiniMax-H3-Max-Turbo` / `768p` / `5`。前后端需共同发布，以识别新协议与第四档位。

保留其它模型、原有聊天模型及其地址/key、数据库、Redis、支付、Logto、JWT、内部服务、抖音及全部云桌面配置。回退默认选项时不要删除 RunningHub provider/model 声明，已提交任务仍需要其原账号路由恢复。
