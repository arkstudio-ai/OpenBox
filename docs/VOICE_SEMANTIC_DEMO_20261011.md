## 验证方式与边界

调用真实的 `qwen-audio-3.1-realtime-plus` 与 `qwen3.8-omni-flash-realtime`。工具执行器仅操作内存中的虚构任务和卡片，未创建或修改平台业务数据。

预先定义了 21 类场景，保留每次运行的配置、源文件快照、函数调用、结果、回复文本和生成音频：

1. 两轮完整对照：每轮 42 条文字输入、20 条语音输入，共 124 条运行记录。
2. 连续音频诊断：针对 3 类场景、2 个模型增加 6 条语音运行记录。
3. 合计 **130 条场景运行记录，其中 46 条使用音频输入**。另外 6 条接入调试记录单独保留，不计入这 130 条。

文字输入用于隔离语义和工具调用；语音输入使用本机 Tingting 合成的 16 kHz PCM，真实进入模型的 smart_turn / semantic_vad。所有回复请求都启用文本和音频输出。没有使用真实麦克风、扬声器回声、嘈杂环境或真实业务执行器。

旧版对照仅抽取当前工作区真实的匹配函数执行，**不是完整旧版应用与新版应用的端到端 A/B 测试**。每种组合只运行一次；第二轮同时改变提示词、业务上下文和工具结果结构，因此不能把分数变化归因于某一个改动，也不能作为模型总体能力排名。

## 三组实验

| 组别 | 做法 | 目的 |
| --- | --- | --- |
| main：初版 | 简短自然交流提示词；模型自主调用 5 个业务工具；没有中文意图正则 | 验证去掉词表后是否能理解和执行 |
| refined：工具契约调整 | 明确对象歧义的澄清原则；增加卡片版本、聚焦对象；区分决定记录与操作排队；补充修改旧卡片的对象关系；结构化后台结果事件 | 验证能否通过工具与上下文设计改进，而不恢复词表 |
| continuous：连续音频诊断 | 沿用 refined 的语义配置，在用户每句之间持续发送静音音频，模拟持续打开的麦克风 | 检查前两组输入停止、续答超时和轮次错误的影响 |

工具执行器只做 JSON Schema、用户归属、卡片状态、选项 ID、版本和调用去重校验，不读取用户原文决定执行哪项业务。测试断言中的字面检查仅用于核对预设名字、时间等参数，不参与模型路由或工具执行。

## 结果统计

“结构通过”只检查工具名称、参数、执行返回与预设是否吻合，不表示回复内容一定正确。“文本复核通过”进一步检查模型实际回复是否忠于输入和工具状态，由本次代码助手阅读记录判断，**未对主观音色与听感打分**。因初版受理编号与任务编号存在契约歧义，部分未通过项同时暴露的是 Demo 设计问题。

| 组别 | 模型 | 输入 | 工具及参数结构通过 | 加上回复文本复核后通过 |
| --- | --- | --- | ---: | ---: |
| 初版 | Audio 3.1 | 文字 | 20 / 21 | 13 / 21 |
| 初版 | Audio 3.1 | 语音 | 9 / 10 | 8 / 10 |
| 初版 | Omni 3.8 | 文字 | 14 / 21 | 7 / 21 |
| 初版 | Omni 3.8 | 语音 | 7 / 10 | 5 / 10 |
| 工具契约调整 | Audio 3.1 | 文字 | 20 / 21 | 16 / 21 |
| 工具契约调整 | Audio 3.1 | 语音 | 8 / 10 | 7 / 10 |
| 工具契约调整 | Omni 3.8 | 文字 | 17 / 21 | 13 / 21 |
| 工具契约调整 | Omni 3.8 | 语音 | 7 / 10 | 6 / 10 |
| 连续音频诊断 | Audio 3.1 | 语音 | 3 / 3 | 3 / 3 |
| 连续音频诊断 | Omni 3.8 | 语音 | 3 / 3 | 2 / 3 |

两轮完整实验共 5 条运行因输入/协议问题未完成：Omni 的两个场景各超时两次，Audio 一次遇到 `Cannot create response while user is speaking`。这些计为完整测试未通过，**不计作已经证实的语义理解错误**。连续音频诊断中的 6 条均跑通工具与回复往返，但其中 Omni 的一条仍把“剪辑已完成”说成“还在剪辑中”。连续音频的效果还需更大样本验证。

## 支持移除硬匹配的证据

| 场景 | 旧规则隔离执行结果 | 原生模型实际表现 |
| --- | --- | --- |
| “解释一下闭嘴这个词是什么意思” | HUSH 命中 | 两款模型均正常解释，没有静音或误执行业务 |
| “就按你刚才那个方案办” | consents 不认可 | 两款模型均能选中正确卡片并提交 approve；执行状态播报另行检查 |
| “不要第一个，第二个就行，项目叫春季上新” | placement_choice 无法识别 | 初版两款模型均提交 new_project 并保留项目名；第二轮部分改走 submit_task，暴露工具职责重叠 |
| “换个更温柔的语气跟我聊” | about_the_call_voice 归为换音色 | 两款模型均自然回应，没有让用户去设置页，也没有创建任务；效果可在 Demo 试听 |
| 前文询问提醒名称，用户只说“春雨” | is_fragment 判断为片段 | Audio 能补全前文时间、事项和名称并调用工具；Omni 有漏调用 |

同一句包含否定不意味着整句拒绝。“不用给我解释原理了，消息就按原样发出去”在两款模型中均能提交发送决定。两轮都没有用于判断“确认／拒绝”的中文词表。

“先别说了，我看一下”之后再问任务进度，在连续音频诊断中两款模型都能继续查询和回答，没有持久静音状态，也没有恢复口令。模型可能给出简短口头回应；本实验不声称实现了绝对零声音的静默。

## 仍需解决的问题

### 1. 对象歧义不能靠有效 ID 检查解决

初版 Audio 在同时存在两张卡片、用户说“就按那个来吧”时直接选择 C1。C1 确实属于当前用户且尚未处理，所以结构校验无法阻止这次猜选。

增加明确的对象上下文和澄清原则后，Audio 改为询问哪张卡片。连续音频诊断中，两款模型都询问了具体对象，没有代选。这支持使用语义澄清，但小样本不能证明以后绝不猜选。

### 2. 选择的补充参数与修改原方案职责重叠

第二轮强调“修改原方案使用 submit_task”后，两款模型在文字输入中把“第二个，项目叫春季上新”当成新建/修改请求，绕过了原来的选择卡；Audio 的语音输入也出现同样情况。

应在工具和卡片结构中明确：选项允许携带哪些字段，哪些变化构成修改原操作。新项目的名称可以是选项自身的参数；改变已确定的收件人则是修改原操作。继续堆叠例句不能代替清楚的工具边界。

### 3. 受理、任务创建、业务完成存在混淆

初版返回 `status=accepted` 与 `task_id=D1`，但 Demo 本意是请求受理，尚未完成真实业务。这个编号命名本身容易让模型理解成“任务已经创建”。第二轮区分 decision 与 operation 后，自然确认的发送场景改善，但提醒设置、方案修改等场景仍有提前宣称完成。

真实接入应明确区分请求 ID、已创建的资源 ID、当前操作状态与实际已发生的结果。例如受理创建请求时不提前返回一个看起来是已创建业务资源的 ID；后续完成事件明确“创建任务完成”还是“任务执行完成”。

不能把“模型调用了正确工具”当成播报准确。连续音频诊断里，Omni 同时查询并提交任务正确，但仍把剪辑完成误述为剪辑中。

### 4. gone 太含糊

过期卡片测试中，Audio 收到 `gone` 却说通知已经发送；Omni 也曾解释成卡片已经处理。这是结果表达与模型理解共同的问题。

工具应区分已过期、已回答、状态冲突，并提供这次操作是否实际执行及当前已知结果。只返回一个含糊状态，再用固定“没办好”话术修正，会继续增加补丁。

### 5. 工具调用仍可能遗漏

Omni 在部分短回答、跨轮确认和恢复后查询中只给出口头承诺，未调用工具。增加工具说明改善了部分场景，也没有消除全部遗漏。这是需要回归评测的实际问题，不能因为官方支持 Function Calling 就假设所有业务请求必定调用工具。

### 6. 后台结果与音频调度需要保留

初版直接插入 system 角色的完成资料并要求生成回复，两款模型仍继续聊猫，没有播报任务结果。第二轮明确后台事件的来源、数据和告知意图后，均能转回任务结果；Audio 仍有完成对象表述不清的问题。

持续音频诊断跑通了之前未完成的输入和续答场景。因此应保留音频轮次同步、播放队列、响应取消、工具结果关联以及后台事件调度。这些机制不依赖中文词语匹配。

## 建议的改造边界

可以移除：HUSH 与 hushed 状态、确认/拒绝词表、选择正则、字数判断、两次发言的确认有效期、动作词分类，以及根据助手说出某句话便自动补执行业务的机制。

应保留并整理：原生语义轮次、工具定义与调用、用户及对象权限、稳定对象 ID 和版本、幂等性、实际业务状态、异步结果交付、音频播放与连接恢复。

提示词保留角色、自然表达、用户偏好、能力范围和事实准确性。工具说明写清职责，返回结构化事实，让模型自然组织回复。发现遗漏与误报后通过独立评测改进，不在通话业务入口补新的中文词表。

本 Demo 验证了方案方向和风险点，**尚未完成生产主助理链路、真实麦克风、多人噪声与长时间通话验收**。主观自然度以页面原声试听为准，不能仅凭字幕认定变得更温柔或更自然。

## 复跑

在仓库根目录执行，使用新的输出目录保留旧证据。脚本使用现有百炼配置，调用会产生模型用量；没有平台业务写入。

```bash
backend/.venv/bin/python -B demos/realtime-voice/semantic_demo.py \
  --out .local-dev/voice-semantic-demo-20261011/new-run \
  --variant refined --mode both --continuous-audio
```

生成展示页并启动本地服务：

```bash
backend/.venv/bin/python -B demos/realtime-voice/semantic_report.py \
  .local-dev/voice-semantic-demo-20261011 main refined continuous

backend/.venv/bin/python -B -m http.server 8792 --bind 127.0.0.1 \
  --directory .local-dev/voice-semantic-demo-20261011
```

现场服务已在 8792 运行时无需重复启动。工具结构断言由脚本生成；回复文本复核单独存放于 `reviews.json`，不参与模型执行，也不会在复跑时假装完成主观评测。

每个运行目录包含 `manifest.json`、源文件快照、`results.json`、脱敏事件日志及 WAV；原有失败记录没有被覆盖。接入调试中的 assistant 历史消息类型错误已在 Demo 中修正为 `output_text`，握手超时仅在尚未执行工具时重试。
