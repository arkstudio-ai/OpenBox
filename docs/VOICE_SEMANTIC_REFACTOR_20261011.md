# 语音助手项目级语义改造与验收

日期：2026-10-11。对应用户确认的语义 Demo 方向；包括语音语义改造、待处理任务选择修复与 Audio 3.1 默认模型策略。代码合并不等于生产发布。

## 1. 已落实的设计

输入音频 → 阿里云原生实时模型理解上下文 → 原生工具调用 → 服务端校验身份、对象、状态和版本 → 实际执行回执 → 自然播报。

用户的句子和模型的口头承诺不会被服务端解析成业务命令。服务端也不会因为没出现某个中文动词、回答太短或出现否定词而改写模型的业务决定。

| 模块 | 删除或替换的旧行为 | 当前行为 |
| --- | --- | --- |
| `voice/bridge.py`、`turns.py` | 持久静音/恢复状态、`HUSH` 等文本触发器 | 不再把“闭嘴”等字面内容当开关；保留 VAD 插话、播放清理、静默保活和断线恢复 |
| `voice/router.py`、`handover.py` | 第二个模型重新判意图、另行规划转交、按口头承诺补执行 | 两个模块及运行时接线已删除；实时模型直接调用现有工具 |
| `voice/tools.py` | 短句、填充词、动作动词、换声词、片段过滤 | 使用工具参数 Schema；“春雨”“那就这样”等由模型结合上下文理解 |
| `voice/cards.py` | 中文同意/拒绝/选项正则、最近两轮有效的限制、按否定词自动取消 | 模型给出明确的卡片、版本、选项 ID；服务端验证真实状态；不会根据转录单独提交或取消 |
| `assistant/placement.py` | 新建对话/新建项目/否定句的文字匹配 | `destination_confirmed` 表达模型理解的用户选址；未选择时仍通过原有卡片询问 |
| `assistant/request_answers.py` | 从标题词汇推断风险、用“我登好了”等固定句判断完成 | 后果元数据、`completion_reported`、真实用户消息来源；接管恢复工具继续检查页面 |
| `voice/prompt.py`、`phrases.py`、`assistant/runtime.py` | 固定句数、复读示例、正常对话模板、重复确认引导 | 描述能力、事实和表达偏好；模型按上下文自然组织语言 |

手机和网页共用后端协议，无新增客户端消息类型。界面上的麦克风静音按钮是采集控制，未改成语言意图功能；此轮删除的是服务端的语义静音/恢复状态。

## 2. 保留的业务与状态校验

- 用户、工作区和对话归属，真实用户消息来源、卡片代次、到期状态、选项合法性、并发和幂等约束。
- 卡片版本由内容计算，变更后旧版本不能作答；重新展示变更内容后必须有新的用户发言。
- 从待处理列表消失不等于“已确认”：读取实际状态，区分过期、已答、已替代、不可访问和冲突。
- 卡片回答按音频轮次绑定原话；较晚到来的另一句转录不能覆盖之前的回答。
- 新项目选项可同时携带用户给出的 `project_name`，与选择在同一事务中保存；重复提交不同名称会冲突。
- 任务提问必须明确 `question_id`；后台事件、问候和进度播报不能自行发起业务写入。
- 老的任务问题如果没有后果元数据，保守地保留确认；新问题由模型声明 `requires_confirmation`。实际执行工具的权限规则继续生效。

删除“确认/选择的中文匹配”不等于删除执行权限或删除所有卡片。后者承载目标、选项、影响和真实用户决定。

## 3. 工具回执与说话方式

| 回执 | 证明了什么 | 尚不能证明什么 |
| --- | --- | --- |
| `accepted` / `queued` | 已接收请求并排队 | 已开始、已完成、定时安排已成功生效 |
| `decision_recorded` | 已记录这张卡片的选择 | 消息已发出、项目已创建、后续任务已完成 |
| `expired` / `superseded` / `conflict` | 本次回答没有按原目标应用 | 可以改答另一张卡片或悄悄重试 |
| `already_answered` | 已存在回答，本次未再次应用 | 原操作执行成功 |
| `result_unknown` | 没有取得可确认的结果 | 失败或成功；应先只读查询 |

后台结果带请求标识、来源、状态和事实，正常播报不提供必须复读的句子。单次响应的提示也携带完整会话角色与工具契约，避免续答丢失规则。

还保留的固定中文属于通话终止/异常兜底：时间到、积分用尽、断线重连、暂未取得结果、结果无法语音播报等。它们不会触发业务，不是中文意图词表。

## 5. 真实模型与本地网页验证

`demos/realtime-voice/project_probe.py` 使用项目实际 `RealtimeProvider`、`Bridge`、提示词和工具实现，输入 macOS 合成语音，持续发送 PCM 静音帧。仅业务存储/执行器为内存沙箱，没有发送实际消息或创建业务项目。真实模型调用与普通单元测试分开记录。

### 最终 Audio 3.1 实测

| 场景 | 检查结果 |
| --- | --- |
| “闭嘴是什么意思？解释一下这个词” | 正常解释，没有静音状态或业务调用 |
| “语气温柔一些，别这么机械” | 自然回应，未当成业务任务 |
| “就按你刚才那个方案办” | 对已展示的明确卡片调用正确选项 |
| “不用给我解释原理了，消息就按原样发出去” | 正确确认发送，没有被“不用”误取消 |
| “不要第一个，第二个就行，项目叫春季上新” | 正确选中新项目，并携带名称 |
| 两张卡片下“就按那个来” | 先澄清，没有写入 |
| 提醒命名上下文下“春雨” | 转交完整的提醒请求，不过滤短回答 |
| 交办新品宣传计划 | 调用 `assistant_ask`，返回排队回执 |

最终这 8 项**结构检查 8/8**。这是小样本，不能解释为线上成功率。逐句审阅仍发现“春雨”回执后说“每天早上九点会提醒您”的过度承诺；它没有真实完成创建，不能当作播报完全合格。两卡澄清也偏向先问第一项，虽然没有执行，问法仍可更中性。

### Omni 的剩余限制

最后一轮双模型测试，Audio 结构检查 8/8，Omni 4/8。Omni 出现一次无转录/无回应超时、明确表达后漏调用工具、短回答漏执行，以及两张卡片下自行选择第一张。前面一轮还出现过“排队请求被说成已完成”。最后一轮提示保留会话规则后，该完成误报场景通过，但不足以证明问题根除。

没有为了让测试全绿重新加中文正则、隐藏失败或反复试到成功。当前默认模型仍是 Audio 3.1；Omni 不标记为已全面验收。语义层仍依赖模型质量，服务端状态校验不能替代模型对含糊表达的理解。

## 6. 依据与复现

官方协议明确由模型产生 Function Calling，客户端回传 `function_call_output` 后触发续答；VAD 场景无需按中文字词手动提交音频。这轮保留协议级轮次管理，将业务意图交回模型：[阿里云客户端事件](https://help.aliyun.com/zh/model-studio/client-events)、[Audio 实时交互指南](https://help.aliyun.com/zh/model-studio/qwen-audio-realtime-user-guides)。

```sh
backend/.venv/bin/python demos/realtime-voice/project_probe.py \
  --model audio --out .local-dev/voice-semantic-fresh-run
```

## 7. 全用户 Audio 3.1 默认策略

- 设置目录、实际通话和 WebSocket `ready.model` 共用同一份选择结果，默认均为 `qwen-audio-3.1-realtime-plus`。
- 旧环境中的 `VOICE_MODEL=...omni...` 和本次发布前保存的 Omni 选择不再覆盖产品默认值；已有 Audio 音色仍保留。
- 使用固定的偏好标记 `assistant_voice_model_rollout=audio-3.1-20261011` 区分发布后的明确模型选择；不要在后续发布中随意修改标记，否则会再次重置用户选择。
- 用户发布后主动选择 Omni 时，继续尊重该选择并恢复其 Omni 音色。只改音色的旧客户端不被视作重新选择模型。
- 各模型音色、语言、外观和引导等偏好不被删除；无需数据库结构迁移或批量覆盖偏好。现有通话沿用接通时的模型，新策略从后续通话生效。
- 上线需要发布这份后端代码；合并 main 本身不会修改正在运行的生产实例。

## 9. 根据上下文安排项目与会话（2026-10-12）

用户只需说明要做什么。主助理结合项目说明、项目简报、会话最初的需求、最近消息和当前跟进任务判断归属，不要求项目标题包含用户说的词，也不使用中文意图词表。

| 情况 | 行为 |
| --- | --- |
| 明确是在继续某件已有工作 | 关联并续办原会话，不重复建任务 |
| 已明确选定项目，要做一件独立的新工作 | 在该项目新建会话，不重复询问归属 |
| 有相关项目，但用户还没有选定 | 模型根据当前需求组织问题，提供原项目新会话、新项目加会话和取消选项 |
| 没有找到合适项目 | 询问是否新建项目及会话，不塞入无关的默认项目；同意前不创建 |
| 有多个可能的项目或会话 | 先自然澄清指代，不按展示顺序猜测 |
| 只讨论、咨询或探索想法 | 直接交流，不自动创建任务 |
| 用户要求交付文字方案 | 仍按任务安排；不联网、不改文件只约束执行方式 |
| 用户把命名交给助手，或认可上下文中的提议 | 使用合适名称，不要求逐字复述；用户已指定名称时保留原名 |

模型每轮获得有大小限制的项目、会话目录；未读完的页面保留游标，信息不足时再分页或读取相关历史。目录优先于较早的闲聊，但不能挤掉当前输入和用户决定。自动目录不重新注入项目简报正文或助手原始结果；需要时通过只读工具获取。报告、协调和压缩轮次不接收这份跨项目目录。

新建选择沿用原来的原子提交和重试机制。两选项卡片通过持久化的选项身份识别“新建项目”，不再假定它必定是第二项；已有三选项卡片继续兼容。保留用户来源、所属空间、卡片版本、取消和重复提交校验。

验证结果：

- 扩大回归初跑：1,373 通过、13 跳过、3 失败。失败分别暴露了紧预算下导航挤占决定、自动回放助手原始结果、自动回放项目简报的问题，均已修正；包含这些失败项的专项复验 42 通过。
- 后续相关回归 138 通过；最终导航与语音专项 87 通过；补充长历史预算回归后，最终发布专项 63 通过。这些集合有重叠，不相加计算总通过数。Python 编译及 Git 空白检查通过。
- 使用实际主助理模型 `openai/gemini-3.8-flash-high` 和真实工具，在隔离 SQLite 的合成数据上检查上述 9 个场景，9/9 通过。澄清和讨论场景同时人工检查了回答内容。这是小样本，不代表线上准确率，也不是 Audio 3.1 的 9 次语音实测。
- 本地浏览器中，交办新的开业方案后出现模型生成的提议；确认后创建一个项目和会话，并执行完成。随后用“把刚才那份方案的活动预算补上，预算按两万元，其余要求不变”续办，仍使用同一会话，完成预算更新；会话总数未增加。
- 浏览器最初发现“文字方案”被当成普通讨论，且长历史挤掉当前目录。已据此修正任务判断提示和目录优先级，并补充回归测试。
