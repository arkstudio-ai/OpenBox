# 同模型压缩、80% 阈值与请求预算核查

> 文档类型：实施 / 验收记录。版本、测试数量和部署状态只对应文内记录时点。

日期：2026-09-17。分支 `codex/integrate-agent-refactor`，修复基线 `d50f49b`。
本文记录该基线之后的修复与验证结果。

## 已实现的行为

自动压缩按完整的下一次模型请求判断，默认在模型窗口的 80% 触发。
以当前本地配置的 `openai/gemini-3.8-flash-high` 为例，窗口为 1,000,000，
阈值为 800,000 tokens。200 条聊天分页限制不参与这个判断；250 条消息
只要总请求仍低于预算，就继续全部发送，不因条数截断。

| 项目 | 当前行为 |
| --- | --- |
| 摘要模型 | 使用当前有效对话模型；每个分块和最终汇总均一致 |
| 自动阈值 | `min(context_limit × 0.8, context_limit − reserved_output)` |
| 输出预留 | 实际请求输出上限和显式 `reserved` 取较大值 |
| 最近原文 | 默认最多占窗口 16%，仍尊重显式 `preserve_recent_tokens` / `tail_turns` |
| 摘要输出 | 默认配置 8192 tokens；按窗口和当前模型的思考预算调整实际请求额度 |
| 连续重压缩 | 默认最多再尝试 1 次，即连续最多 2 次；仍超预算则停止并报错 |
| 请求前缀 | 复用本轮已准备的 system、工具 schema、variant、cache key 和 native tool plan |
| 摘要工具行为 | 保留 schema，设置 `tool_choice="none"`，不执行工具 |
| 成功条件 | 完整终止、非空、比源内容更短，且稳定事件范围原子替换成功 |
| 原始记录 | 后续模型使用摘要与保留尾部；历史聊天仍可分页查看 |

部分小窗口模型会因输出预留而早于 80% 触发。例如窗口 128,000、输出预留
32,000 时，输入阈值为 96,000。80% 是比例上限，不覆盖实际输出空间约束。
当前本机模型配置带有 16,000 的思考预算，沿用适配器的 8,000 输出保留后，
摘要请求实际输出额度为 24,000；没有把 8192 当成包含思考的绝对硬上限。

本地 `backend/openbox.json` 已启用 `auto=true`、`prune=true`、
`threshold_ratio=0.8`、`retain_ratio=0.16`。原配置已备份在
`.local-dev/config-backups/20260917-222140-compaction/openbox.json`，保持仅本机可读。
其他本地连接配置未改动。

## 请求计量与恢复流程

`backend/agent/context_budget.py` 复用实际 Responses / LiteLLM 请求构造函数，
计入 system、工具定义、消息角色、文本、工具参数、工具结果和图片占位预算。
统一使用本地 `o200k_base` 作为代理 tokenizer，缺少 tokenizer 时使用兼顾
UTF-8 字节数的回退估算，避免中文直接除以 4 的明显低估。

同时将最近一次有效 provider usage，加上之后的新输入和新工具结果，作为
下限。缓存 token 不重复相加，压缩前保留尾部上的旧 usage 不再误触发新压缩。
最终发送前还会对 checkpoint 固定的实际请求复测，避免准备期间增长漏检。

达到阈值后：

1. 裁剪允许裁剪的旧工具结果，重新加载规范会话并计量。
2. 如仍超阈值，冻结可替换的稳定事件范围，保留最近尾部，调用同模型摘要。
3. 成功后重新加载“摘要 + 保留尾部”，按完整请求再次计量。
4. 自动运行仅在预算内继续发给模型；仍超阈值时进行有界重试，避免无限压缩。

手动压缩同样在完成后更新完整上下文用量，但按原有语义暂停，让用户查看
摘要。下一次输入仍通过相同自动预算检查。Provider 自身报告超限的恢复路径
保留原有有限次数保护。

源内容超过摘要请求窗口时，按完整序列化数据分块，连同前缀与摘要提示一起
计量；不丢弃超大单条消息、工具参数或结果中间段。分块失败、流中断、输出
截断或最终合并仍超限时，不提交不完整摘要。取消、用户归属、run generation
fence 和事件范围 CAS 继续生效。

## 回归发现与修复

- 旧会话迁移修复后再次读取，部分用户轮次缺少锚点。现在同时从
  `turn.started` 恢复身份，并持久化已确认的父消息关联；跨轮次校验仍严格。
- 工具 JSON schema 中名为 `type` 的属性可能是嵌套对象。图片计量现在先检查
  标签类型，避免真实浏览器请求触发 `unhashable type: dict`。
- 首轮真实摘要保留了核心参数，但擅自把验收口令扩展为第三项待办，并弱化
  “不要调用工具”的限制。已补强最终与分块摘要指令：逐字保留禁止事项、
  保留数值和执行顺序、区分事实与推测、不从背景参数推导新增任务。

## 结论适用范围

- Gemini / DeepSeek 的 token 数仍是代理估算，不是服务商精确 tokenizer；
  每张图片的 4096 tokens 也是预算估值。Provider usage 和超限恢复继续兜底。
- 复用的是本轮准备的前缀；尚未像 DeepSeek 一样跨重启持久化并原样回放上一
  请求 header。动态工具或系统提示变化仍可能影响缓存命中，没有实测命中率承诺。
- 超多分块汇总仍放不下时会安全失败，不实施无界递归摘要。
- 真实模型质量验证属于合成数据冒烟测试，不能据此保证任意长对话摘要零遗漏。

## 前端“上下文优化”展示

2026-09-17 追加：新版 `frontend-v2` 将压缩请求与摘要配对成独立的过程项，
从摘要消息创建时就使用 `agent=compaction` 识别，不等待完成后才写入的
`summary=true`。摘要正文从最终答复、执行说明、回复操作栏中排除，统一
进入默认折叠的“上下文优化”；用户展开后仍能查看流式/已保存的摘要。

自动压缩及其合成继续消息保留在同一轮，后续模型或工具步骤继续执行，
最终答复的消息 ID、token 数据和操作仍归属于真正的答复。手动压缩也归入
上一轮的处理区域，不在最终答复下方新增独立轮次。失败、中断单独
显示，未完成的旧摘要不会因新一轮开始而重新显示为“正在优化”。分页未
加载压缩请求时，可凭摘要的父消息 ID 还原同一个过程项。

折叠使用现有 `TraceShell` 样式，支持键盘、`aria-expanded`、关联面板和
隐藏内容的焦点隔离。关闭时不挂载大型摘要 Markdown，流式更新和完成事件
不自动改变用户的展开选择。

参考依据：

  将压缩报告为 `contextCompaction` 过程项，并发送开始/完成事件。固定版本
  开源 `compact.rs:243`、`:398` 对应这两个生命周期事件；这不代表复用了
  Codex 桌面端未公开的 UI 组件。
- 本地 DeepSeek harness 的
  CompactionItem.tsx（外部源码参考：`deepseek-harness/packages/client/ui-chat/src/client/chat/CompactionItem.tsx:31`）
  默认折叠摘要，并保留历史记录；其手动命令也避免与摘要重复显示。

前端新增 18 项行为测试；全量 **133 个测试文件、929 项通过**。生产构建、
TypeScript、i18n 对齐检查及 ESLint 通过（已有 41 条警告，无错误）。本地
浏览器已验证旧会话显示、点击展开、回车折叠，以及调用真实模型压缩后
新增一条完成状态的过程行。刷新后摘要仍默认折叠，继续输入后模型在 6.0 秒

## Turn 内自动压缩与统一过程区复测

2026-09-17 再次调整：思考、工具调用和上下文优化放在同一轮的处理区域，
均位于最终答复之前。手动历史压缩也遵循这一分组。压缩进行时，已结束的
思考和工具调用不会继续显示为正在运行。

用户授权临时缩小模型窗口后，将 `openai/gemini-3.8-flash-high` 的窗口从
1,000,000 调为 200,000，保持 80%（160,000 tokens）阈值、同模型摘要与
真实 provider。各压力会话先在本地 Docker PostgreSQL 中装入 260 条合成
历史消息，再从浏览器发送新任务；没有调用手动压缩接口，也没有伪造
provider usage。下表用量包括模型的 system/工具等固定开销，不只计算聊天文本。

| 场景 | 浏览器实测结果 |
| --- | --- |
| 历史较长后发送新任务 | 自动压缩一次后继续答复，口令、项目、预算、待办顺序均正确；完成后当前上下文 52,999 tokens |
| 未到阈值 | 输入 152,602 tokens，正常回答，无压缩 |
| 新输入跨过阈值 | 从 76% 升到 83%，看到折叠的“上下文优化”运行状态；完成新任务后降到 51,129 tokens（约 26%） |
| 工具返回跨过阈值 | 真实 `web_fetch` 返回 46,048 bytes 合成数据，环形占用显示 100%；在同一个 turn 自动压缩后续跑，准确复述仅在结果末尾出现的 `END-QA-0917`，最终当前上下文 18,750 tokens（约 9%） |
| 刷新还原 | 工具调用、上下文优化仍在同一轮且默认折叠；最终回答与摘要分离 |
| 压缩中停止再继续 | 首轮暴露了后台停止超时，修复后浏览器点击停止即可结束压缩并恢复空闲；再次输入正常压缩、续跑，口令、项目代号、待办顺序保留 |

停止测试额外发现并修复了后台问题：普通对话已经用可中断流等待下一段输出，
最终摘要和分块摘要却没有接入 turn 的 abort 信号，导致前端先停止、后台仍等
provider，日志出现等待 driver 停止超时。现在两类摘要复用相同的流取消机制，
取消 consumer 时也会关闭等待中的 provider；loop 在停止后不再进入下一步。
测试覆盖无首 token、分块摘要、API 停止后继续输入、直接取消消费任务四种情况。

真实工具输出测试先尝试了无影 `bash`，但沙箱返回
`Server disconnected without sending a response`，该次不计通过；随后用
仅绑定本机回环地址的合成数据服务及现有 `web_fetch` 工具完成上述真实循环。
无影连接问题当时未在这次 UI/压缩改动中修复。2026-09-18 已另行修复
本地 Session Manager 隧道换新，浏览器真实 `bash` 调用通过，详见
[无影通道说明](../../operations/WUYING_SANDBOX.md#local-forwarding-through-alibaba-session-manager)。
