# 长会话、200 条分页与上下文压缩核查

> 文档类型：实施 / 验收记录。版本、测试数量和部署状态只对应文内记录时点。

核查日期：2026-09-17。当前分支 `codex/integrate-agent-refactor`，基准
`origin/main` 为 `9f9452489fdca932cc9c2d4ff0eae468da738879`，修复基线为
`d50f49b`。验证包含工作区中此前的响应速度优化。

## 原始故障与 main 的修复

main 在 `6ab602efb9bb4993c9eead3677dbc547a5010824`（2026-09-14）修复了
`get_messages()` 默认只读最早 200 条的问题。这是 **200 条 Message 行**，
不是 200 轮问答；一个工具步骤也可能新增一条 assistant Message。

旧代码使 Agent、工具输出裁剪、压缩、问答续跑等内部调用者一直看到同一个
历史前缀。新输入可能已保存，但模型看不到；如果前缀最后一轮已经完成，
Agent 甚至会直接判定无需继续。压缩请求和工具结果落在第 200 条之后时，
也可能被漏掉，因此无法通过压缩恢复正常推进。

该提交同时处理了三个问题：

- 内部读取默认 `limit=None`，完整读取历史。
- HTTP `/message` 明确保留 `offset/limit` 分页，默认一页 200 条。
- 全量读取 Parts 按会话查询，避免为每个 Message ID 展开一个 SQL 参数。

随后 `6aee878` 加入 `CONTEXT_STALLED` 保护，在多步请求的输入 token 数反复
不变时停止重复消耗。它是兜底检测，不替代完整历史读取。

## 当前分支的行为

`backend/session/session.py:get_messages` 保留内部无默认上限和稳定排序。
`backend/agent/loop.py` 从 `load_canonical_model_surface` 读取完整、有归属校验
的事件前缀，再根据已完成的压缩替换构建模型上下文；没有 200 条截断。

`freeze_compaction_event_range` 同样从完整事件投影冻结压缩源。自动压缩按
模型的 token 容量与预留空间触发，和页面条数无关。后续核查修复了旧 usage
锚点及摘要失败处理，并统一使用对话模型，详见
[同模型压缩核查](AGENT_COMPACTION_REVIEW.md)。
压缩成功后模型使用摘要及保留的最近原文；完整聊天记录仍可分页回看。

Web 和移动端的 `/history` 默认读取最近 8 轮，使用 `before` 翻阅旧记录、
`after` 追赶最新消息。这套 UI 分页不决定 Agent 能看到的上下文。

循环里的 `step > 200` 与 main 一致，限制的是**单次运行**的执行步数；
每次运行从 0 计数，不是会话总条数或总轮数限制。

## 本次发现并修复的遗漏

200 条截断故障没有复发，但重构导入旧会话时，
`_sanitize_read_model_locked` 和 `_surface_snapshot_locked` 又使用了
`Part.message_id.in_(全部消息 ID)`。超长历史会超过数据库参数数量上限，
在进入模型请求或压缩前失败。当前安装的 asyncpg 明确限制单条查询最多
32767 个参数。

两处查询改为关联 Message，按会话和用户筛选 Parts。Message 与 Part
两侧的归属条件全部保留，参数数量不再随历史长度增长。没有新增分页、
截断或删除历史。

回归先在 SQLite 降低真实连接参数上限后复现：原有完整历史读取成功，
重构导入报 `too many SQL variables`；修复后通过。另在 Docker PostgreSQL
中用 **32768 条真实 Message 与对应 Parts** 验证完整导入通过。

## 验证

新增 `backend/tests/unit/test_long_history_context.py`，使用 201 轮、402 条
初始历史，保留真实 API 函数、Agent 循环、工具执行、持久化和续跑逻辑，
只替换模型流与沙箱等外部调用：

- 同步和 Web 使用的异步发送都能处理新输入，并看到随后产生的工具结果。
- 本轮完成后，再次发送的新输入也能进入模型请求。
- ask 选项回答经过实际问答续跑 worker，被模型作为工具结果读取且只续跑一次。
- 模拟 provider 上报超限 token，真实自动压缩流程能读取第 200 条以后的源内容。
- 自动压缩保留最近原文、当前用户请求及工具结果，循环继续完成任务。
- 再经手动压缩后，下一条输入能携带最新摘要进入新的模型请求。
- 压缩后翻阅全部历史不漏不重；旧 `/message` 仍返回 200 条一页。
- 超过数据库参数上限的旧会话能导入事件日志。

相关后端回归 97 项通过，覆盖完整历史、分页、压缩选择、事件范围、
事件日志、模型投影及此前的响应速度优化。前端消息 API 与流状态分页
测试 20 项通过。Docker PostgreSQL 单独验证 10 项通过，包括上述新增
5 项和主线压缩兼容 5 项；其中超长导入使用真实的 32768 条消息。

这些测试验证历史可见性和生命周期正确性；模型流为确定性测试数据，
不声称验证了真实模型的摘要质量或所有长度下的响应性能。
