# Trace 批量入库修复与聊天混合压测（2026-09-15）

## 结论

**Trace 的稳定性和核心聊天的承载能力是两件事。此次修复降低了 trace 入库延迟，但混合负载仍会拖慢聊天；当前单实例配置没有通过千人同时聊天测试。**

- 相同的 1,000 用户 × 1,000 事件、约 5,000 事件/秒负载下，全部百万事件入库并逐条回读一致，入库延迟 P95 从 74.51 秒降到 28.98 秒。
- 50 路持续聊天、累计 1,000 次聊天：加入 trace 写入和管理端回放后，回复及历史记录全部正确，但首字 P95 从 2.154 秒增至 2.856 秒，完整回复 P95 从 2.665 秒增至 3.545 秒。
- 1,000 人同时发送一次消息：没有额外 trace 压力时，修复后的版本仅 971 个会话完整成功；加入 trace 压力后降到 953 个。主要错误是业务数据库连接池等待 30 秒后超时。
- 模型使用固定响应替身，没有上游模型或沙箱网络波动，因此这些延迟和失败不能归因于模型服务。

这些是本机隔离测试结果，不能直接作为 gw2 的容量承诺。50 路和 1,000 路指实际同时活跃的聊天请求，不把 1,000 个轮换身份写成 1,000 路同时聊天。

## 已实施的修复

### 1. 批量更新 trace 会话状态（`a604c45d`）

把每批事件中逐会话 `UPDATE` 改为每 500 个会话一次 PostgreSQL `UPDATE ... FROM (VALUES ...)`；SQLite 使用 executemany。事件、会话计数和 spool 文件位置仍在同一个事务中提交。

真实 PostgreSQL 测试覆盖 501 个会话、不同计数、第二批更新失败后的整批回滚，以及重试后不丢失、不重复、不覆盖投影和检查点进度。

### 2. 投影和检查点跳过暂时被占用的会话（`a604c45d`）

投影、检查点新建和检查点进度修复统一使用 `FOR NO KEY UPDATE SKIP LOCKED`。暂时被入库事务锁住的会话由现有轮转机制稍后重试，不阻塞整个投影批次，也不将锁忙当成失败退避。

真实 PostgreSQL 测试验证：一个会话被锁住时另一个仍能投影；释放锁后能补齐；检查点新建和修复均可重试。

### 3. 移除不同用户通知之间的全局串行等待（`4d3e1cb3`）

混合测试准备阶段发现：聊天完成时写站内通知/推送 outbox，会取得移动端登录换绑使用的全局独占锁。即使用户没有绑定手机，也会走这条路径。

现在通知使用全局共享锁及按收件人划分的独占锁；登录、换绑和推送领取保留全局独占锁。一次事务通知多个收件人的入口保留全局独占保护，避免锁顺序反转。

在两组空载聊天测试的累计查询统计中，这部分 PostgreSQL advisory lock 总执行时间从约 985 秒降到约 32 毫秒。这个累计值包含各请求的等待，**不是一次请求耗时**。

该修复消除了跨用户锁等待，但没有改善本机单实例千人聊天的整体通过率。修复前 982/1,000 个会话完整成功，修复后该轮为 971/1,000；两轮都存在连接池超时。不能把锁统计改善解释为千人聊天容量已经达标。

## 测试条件

| 项目 | 设置 |
|---|---|
| 环境 | 本机 Docker，原生 ARM；Docker VM 10 CPU、约 8 GiB |
| Trace worker | 单进程、1 CPU、1 GiB；真实入库、投影、归档、读取 |
| Trace PostgreSQL | PostgreSQL 16，2 CPU、2 GiB，独立于业务库 |
| 业务后端 | 单个 Uvicorn 进程，2 CPU、1.5 GiB |
| 业务 PostgreSQL | PostgreSQL 16，2 CPU、1.5 GiB |
| 业务连接池 | 默认 pool_size=10、max_overflow=20，等待超时 30 秒 |
| 实际聊天路径 | `POST /api/session/{id}/prompt_async`、真实 agent loop、`/api/ws/agent` |
| 查询 | 会话列表、当前会话历史；另有 10 个持续查询任务 |
| 模型 | 3 个固定文本块，共约 200 ms；校验每个用户独有的完整回复标记 |
| 身份/租户 | 合成身份，真实 workspace membership 检查、真实业务表写入 |
| 外部依赖 | 测试鉴权替身、本地 blob；不调用真实模型、沙箱、OSS 或推送服务 |

每组聊天测试使用独立的新会话。修复后的空载和混合测试提前创建相同的四组会话，避免会话列表条数随阶段增长。业务记录在独立测试数据库内，正常本地业务库和现有聊天没有混入压测数据。

混合压力包括：

1. 同一个业务后端进程运行 1,000 个 trace 生产任务，每人产生 1,000 个事件，目标每人每秒 5 个事件。
2. 同时运行真实异步聊天和 WebSocket，并验证最终数据库和历史接口内容。
3. 两个并发管理端回放任务，每次读取 500 个事件及内容，完成后等待 50 ms；读取前一组百万事件数据，覆盖 PostgreSQL 和归档内容。

基线也开启正常聊天的 trace 记录；“空载”仅表示没有额外百万事件写入和连续管理端回放。未叠加真实模型推理、工具执行、视频/图片上传、网络鉴权、Redis 跨进程转发。

千人场景已经过载。完成时延已剔除输入 HTTP 被拒绝的请求，校正明细保存在 `core-latency-validated.json`，原始日志仍保留。延迟分位数只统计收到了相应事件的样本，失败数必须一起看：没有首字/完成事件的请求不会神奇地变成快速成功。基线的无终态 WebSocket 等待上限为 240 秒，混合测试为 90 秒；因此不比较整组运行总时长，也不比较被空闲尾段稀释的后台轮询 P95。HTTP、首字、完成及最终业务数据核对的口径保持一致。

数据库查询日志确认了连接池超时，部分后台 `run_loop` 在开始前取连接失败。当前异常包装器只记录这些早期异常，客户端可能收不到完成事件。这是核心业务的过载处理问题，不能算成 trace 丢失已成功写入的聊天。

## 仍需处理

1. 为聊天执行增加有界并发和可见的排队/过载状态，避免无限创建后台任务后在连接池里等待超时；开始前失败也需要向客户端给出明确终态。
2. 根据业务吞吐预算规划 API 多进程/多实例，并结合 PostgreSQL 总连接数、跨进程消息转发和执行隔离一起验证。单纯放大连接池或只增加 trace worker 不能证明问题解决。
3. 继续优化投影吞吐；单写入者机制没有在本次改成分片。
4. 64 MiB 生产队列在极端瞬时突发下的丢弃边界仍然存在。本次约 5,000 事件/秒通过，不等于之前约 82,000 事件/秒的突发已经修好。

这些容量和过载处理工作尚未在本次实现；本次完成了 trace 批量/锁修复、通知锁修复以及核心业务影响验证。
