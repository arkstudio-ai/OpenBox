# Trace 百万事件压测（2026-09-15）

## 结论

按 **1,000 个用户并发、每人 1,000 个事件，共 1,000,000 个业务事件**实际测试。
当前单个 trace worker 的 **1 核、1 GiB**配置，不能判定满足这个负载的实时记录要求：

- 约 5,000 事件/秒的持续写入：百万事件全部接收，回读确认没有丢失、重复、乱序或内容错误；入库延迟 P95 为 74.51 秒，投影最大积压 658,665 个事件。
- 约 82,000 事件/秒的突发写入：64 MiB 的 emitter 队列填满，两次运行分别丢弃 6.37% 和 15.86% 的事件。丢弃发生在入队阶段，返回接收成功的事件全部入库；突发时的实际丢弃比例随线程调度和磁盘吞吐变化。
- 完整回读暴露了真实的内存泄漏，曾把 worker 推到 1 GiB 上限并 OOM。修复后，同一批百万事件连续完整读取两遍，容器峰值 196.1 MiB，无 OOM。
- 队列过载时，部分受影响会话原先没有缺失提示；已修复并用另一轮百万事件突发测试验证：1,000 个受影响会话全部有缺失标记。

这次修复解决了读取可靠性和监控正确性。**突发丢弃和持续负载下的投影延迟仍是容量限制**，没有通过扩大内存队列或阻塞业务请求来掩盖。增加容量或调整批处理，需要在目标部署环境重新验证。

## 测试条件与范围

| 项目 | 条件 |
| --- | --- |
| 环境 | 本地 macOS ARM 主机，Docker 原生 aarch64 Python 3.12 运行时 |
| trace worker | 1 CPU，1 GiB 内存，禁止额外 swap；真实 WorkerServices 的入库、投影、归档循环 |
| PostgreSQL | 独立 PostgreSQL 16；2 CPU、2 GiB，shared_buffers=512MB；完成 trace 库迁移 |
| producer | 独立容器，1 CPU、1 GiB；同一进程中同时启动 1,000 个 asyncio 用户任务 |
| 写入链路 | 真实 `emit()` → 有界内存队列 → 本地 spool → worker → PostgreSQL → 投影/归档 |
| 默认队列 | 64 MiB emitter 队列、2 GiB spool 容量；生成期间不重试、不分段 flush |
| 事件分布 | 每用户 10 轮，每轮 100 事件；91% 为 request.delta，其余为轮次、输入、模型请求等生命周期事件 |
| 持续负载 | 每个用户每秒约 5 个事件，1,000 个用户同时活跃 |
| 完整校验 | 真实 HTTP events API，每页 500 个事件，2 个并发读取任务，检查每个事件的身份、类型、内容、顺序及去重表 |
| 对象存储 | 隔离 Docker volume 的 LocalBlobStore；包含真实压缩、外置内容和归档读取 |

这是 **trace 写入链路压测**，没有调用模型、创建 1,000 个真实聊天 HTTP 连接、访问业务素材或真实 OSS。测试用后端鉴权桩只服务隔离的合成数据，不计鉴权网络时延。不能将本机数字直接当作 gw2 或真实 OSS 的容量承诺。

时间从开始产生事件计起；入库、投影完成时间取约 5 秒间隔采样的首次完成点，有一个采样间隔左右的误差。

| 全部入库完成 | 253.95 秒 | 283.53 秒 | 248.70 秒 |

| 最大投影积压 | 623,778 | 658,665 | 559,041 |
| 单事件入库延迟 P50 | 117.15 秒 | 37.76 秒 | 106.48 秒 |

持续写入结束后，约再用 82 秒完成入库、207 秒完成全部投影。持续写入阶段，worker 采样 CPU 中位数约为 74%；入库与投影还存在数据库等待，不能将延迟简单归因为 CPU 用满。原始 PostgreSQL 查询统计也记录了 `session_trajectories ... FOR UPDATE` 的明显等待；本次没有仅凭该统计进行锁语义改写。

三轮都没有失败批次或隔离文件。每个新会话还会自动生成一条 `trajectory.started`：持续写入最终有 1,001,000 条存储事件；缺失标记修复后的突发运行有 841,392 条业务事件、1,000 条起始事件和 5,400 条 gap 事件，合计 847,792 条。结束时这两组数据都已全部投影和归档。

突发丢失生命周期结束事件后，某些投影记录仍可能显示 running/streaming；缺失提示说明这部分记录不完整，不能将其当成模型真的仍在执行。缺失标记修复不会补回已经丢弃的事件。

## 发现与修复

### 1. 压缩内容回读泄漏

`_SpoolWriter` 持有 zstd 原生 stream writer，后者又持有 `_SpoolWriter`。原生对象的反向引用不参与 Python 循环垃圾回收，成功读取后缓冲和解压上下文仍然存活。异常路径只清除缓冲也不能释放这个环。

- 修复前，持续写入已经全部完成投影，随后读取约 500 多个会话时，Docker 确认 `OOMKilled=true`、退出码 137。首轮另一组数据虽然没有 OOM，读取后的进程 RSS 也已超过 780 MiB。
- `9ecc4caf` 显式关闭并解除解压器引用；所有结束路径释放缓冲。临时文件只在成功取得结果后交给响应，取消时等待后台线程退出再释放。
- 新增 11 项资源释放测试，覆盖内存/临时文件、成功、来源异常、哈希不符、解压超限、取消、完成阶段取消。

两遍回读使用 **9ecc4caf**，恢复 **1 CPU / 1 GiB**，没有启用诊断 tracemalloc，没有增加容器内存。写入数据沿用上面的持续写入运行，因而此验证只证明读取修复，不重算写入吞吐。

| 回读校验 | 第一遍 | 第二遍 |
| --- | ---: | ---: |
| 业务事件逐条验证 | 1,000,000 | 1,000,000 |
| HTTP 页数 | 3,000 | 3,000 |
| 耗时 | 30.27 秒 | 42.97 秒 |
| HTTP 页读取 P95 | 32.05 ms | 45.48 ms |
| 容器累计峰值 | 194.2 MiB | 196.1 MiB |
| OOM / 读取错误 | 0 / 0 | 0 / 0 |

第二遍期间同时回读另一组突发数据；后者逐条验证 841,392 条业务事件，峰值约 187 MiB。两遍百万事件检查均确认内容与生成器一致、存储序号连续、没有重复且投影完整。缓存容量保持 64 MiB blob / 32 MiB segment，未关闭归档或回避压缩内容。

### 2. 过载缺失提示覆盖不全

emitter 的单个 gap 控制项最多列出 200 个会话，原先省略了其余会话却没有说明列表被截断。

`e78b326e` 增加列表截断标记；入库时使用同一 producer 最近的会话记录补充不确定范围提示。补充提示不伪造每会话的丢失数量，也不影响其他 producer。另保留了旧协议的兼容处理。

回归突发测试中，1,000 个会话都发生过入队丢弃，逐条回读确认全部有 gap；原先的漏提示从 209 个降为 0。相关 emitter/ingest/服务测试 156 项通过。

### 3. 长时间入库时积压指标滞后

原先一整轮 spool 消费完成后才更新入库延迟，磁盘用量也只在开始整轮时检查。大批量消费持续数分钟时，指标可能仍显示旧值甚至 0。

`9f61760a` 在每个批次前更新当前消费文件的等待时长，供指标和 heartbeat 使用；磁盘用量在批次间按已有 30 秒间隔采样。完成时按当前时钟计算仍在等待的文件年龄。没有增加逐批数据库查询。

此项在百万事件实验结束后修复，已通过 52 项相关测试，包括同一长轮次中新增 spool 内容的指标更新及原有吞吐/内存测试；上表入库延迟始终使用每条事件的真实时间戳，积压使用数据库直接计数，不依赖修复前的滞后指标。
